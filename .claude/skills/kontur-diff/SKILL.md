# KONTUR Diff — что изменилось между версиями

Зачем: чтобы дальнейший анализ шёл по фактам. Новая версия — это не «карта целиком», а набор конкретных изменений и дыр в проверках. Дыры тоже часть результата: они становятся задачами.

## Шаги

1. **Найди версии.** `ls maps/`, `CHANGELOG.md` (верхняя запись = новейшая), `git log --oneline -15`. «Новая» = новейшая в `maps/` (не `_QA`), «прошлая» = предыдущая. Если пользователь назвал версии, бери их. Старые карты v22–v35 убраны, их достают из git: `git checkout d7e94c6 -- <путь>`.
2. **Список изменений в коде.** `git diff --stat <prev-коммит>..HEAD -- sources` и сравни папки вида `sources/<имя>-vNN/` (новые, изменённые, удалённые файлы). `build_place.py` в папке версии показывает, что вклеивается поверх базовой карты.
3. **Журнал и сеанс.** Прочитай запись версии в `CHANGELOG.md` и `sessions/<дата>-*.md`: что заявлено, какие решения приняты, что «не сделано сознательно».
4. **Дыры проверок.** Выпиши из раздела «Проверки» и «Открытые вопросы» сеанса, что **не** прогонялось (двухклиентный тест, FPS на iPhone, звук, ручной проход, сторожевой таймер вживую). Не додумывай проверки, которых там нет.
5. **Затронутые зоны.** Для каждого изменения укажи, что оно трогает: раунд (ядро), аномалию, визуал, UI, звук, сетевое взаимодействие. Это нужно `kontur-perf-budget` (где мерить) и `kontur-player-lens` (чьи сценарии затронуты).

## Вердикт на каждое изменение (одна строка)

Одно из: **игроку лучше** / **стабильнее** / **тяжелее** (добавляет нагрузку) / **рискованно** (новая логика без проверки). Если изменение даёт сразу два, назови оба.

## Выход

```
## Что изменилось (vPREV → vNEW)
- <изменение> — <вердикт> — <зона>
Не проверено в версии: ...
Передать дальше: где мерить нагрузку (...), чьи сценарии затронуты (...)
```

Дальше обычно `kontur-perf-budget`. Если пользователь спросил только «что нового», остановись здесь.
